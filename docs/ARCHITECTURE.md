# QE Studio architecture

This document is for people changing the code. It explains how the pieces fit together, the
contracts between them, and where to add things. User documentation is in the [README](../README.md).

## Overview

```
 Browser (React SPA)                         Backend (FastAPI, one process, 127.0.0.1:8765)
 ┌──────────────────────────┐   HTTP/JSON   ┌───────────────────────────────────────────────┐
 │ pages/  components/      │ ────────────▶ │ api/*        thin routers (validation, errors)│
 │ api/hooks (TanStack Query)│ ◀──────────── │ core/*       pure QE/structure logic          │
 │ store/app (zustand)      │   WebSocket   │ jobs/*       job manager, runner, schedulers  │
 └──────────────────────────┘ ◀──────────── │ executors/*  local | SSH | Jupyter transport  │
                                            │ analysis.py  outputs → plot-ready JSON         │
                                            │ db.py        SQLite (SQLAlchemy)               │
                                            └──────────────┬────────────────────────────────┘
                                                           │ commands + files
                                     ┌─────────────────────┼─────────────────────┐
                                     ▼                     ▼                     ▼
                               this computer        SSH host / cluster     Jupyter / Kaggle kernel
                               (bash or Python      (bash runner,          (bash runner started
                                runner)              direct/SLURM/PBS)      from the kernel)
```

Design rules that the rest of this document elaborates:

1. **The target is the source of truth for job state.** The backend never holds the only copy of
   anything a running calculation needs; it can crash or restart at any time.
2. **Pure logic is separate from I/O.** `core/` has no network, database or FastAPI imports and is
   unit-tested directly. Routers in `api/` are thin.
3. **Every transport implements the same small interface** (`executors/base.py`), so jobs, schedulers
   and installers are written once.
4. **Scientific numbers are never invented.** Parsers return `None` for what they cannot find; units
   come from one module (`core/units.py`, mirrored in `frontend/src/lib/units.ts`).

## Backend

### Request path

`GuardMiddleware` (in `main.py`) runs before every request:

- rejects `Host` headers that are not in the allow-list (DNS rebinding);
- requires the per-install token for `/api/*` (except `/api/health`): header `X-QES-Token`, or for
  WebSockets the subprotocol `token.<value>` (browsers cannot set WebSocket headers; a query parameter
  would end up in access logs).

The SPA's `index.html` is served with the token substituted for `__QES_TOKEN__`; the UI reads it from
a `<meta>` tag. Routers return plain dicts serialised with orjson (`FastJSON`), which also handles
NumPy arrays. Errors are `HTTPException`s with a human-readable `detail`; validation errors are
flattened to one message.

Blocking work (ASE parsing, spglib, NumPy analysis) runs in `asyncio.to_thread` so the event loop
stays responsive. Long operations that the user may want to follow (downloads, QE installs) are
`tasks.Task`s with a log polled by the UI.

### Persistence

SQLite in `QES_HOME/qestudio.db` (WAL mode). Tables: structures, documents (saved inputs),
connections, jobs, kv (settings). Timestamps are stored as UTC (`UTCDateTime`). Large data is kept on
disk, not in the database: pseudopotentials in `QES_HOME/pseudos`, fetched job outputs in
`QES_HOME/jobs/<id>/`, local job directories in `QES_HOME/runs/`.

### Executors

`executors/base.py` defines the transport interface used by everything else:

| Method | Purpose |
| --- | --- |
| `connect()`, `close()` | open/close the transport (idempotent) |
| `run(cmd, timeout)` | run a shell command, return stdout/stderr/exit code |
| `write_file`, `read_file`, `listdir`, `download`, `mkdir`, `remove_tree`, `exists`, `expand`, `home` | file operations |
| `launch_detached(workdir, argv, log)` | start a process that outlives the connection |
| `pid_alive(pid)`, `read_small_files(dir, names)` | cheap polling primitives |

Implementations:

- **LocalExecutor**: `subprocess.Popen` with `close_fds=True` and a new session. (Under uvloop,
  children otherwise inherit the server's sockets and a backgrounded shell keeps the HTTP request
  open.)
- **SSHExecutor**: asyncssh with SFTP; known hosts in `QES_HOME/known_hosts` (trust-on-first-use,
  strict, or ignore); optional jump host; login shell so that `module` works. Detached launches use
  plain `setsid nohup … &` commands, because compound commands with redirections can keep the SSH
  channel open.
- **JupyterExecutor**: creates its own kernel through the Jupyter REST API and talks the kernel
  messaging protocol over the WebSocket. Shell commands run via `subprocess` inside the kernel; files
  move in base64 chunks of 512 kB. If the kernel disappears (Kaggle restarts, culling), the executor
  notices within a few seconds (it asks the REST API when the socket is silent), starts a new kernel
  and re-sends the request **only** when that is safe: when the kernel never started executing it, or
  when the operation is idempotent. Otherwise it raises `OutcomeUnknownError` so that, for example,
  a job is never launched twice.

Executors are pooled per connection (`connections.get_executor`) and recreated when a connection's
configuration changes.

### Job lifecycle

```
created ──submit──▶ submitting ──▶ queued ──▶ running ──▶ done | failed | cancelled
                        │                        │
                        └──▶ failed              └──▶ lost   (runner vanished)
```

1. `JobManager.create` validates the steps, resolves pseudopotentials and stores the job.
2. `submit` creates `<work_root>/<stamp>-<name>-<id>/` on the target, uploads inputs and
   pseudopotentials (`pseudo/`), rewrites `outdir` to `./tmp/` and `pseudo_dir` to `./pseudo/`
   (`jobs/inputs.py`), writes the runner script and hands it to the scheduler adapter.
3. The **runner** (`jobs/runner.py`) is a self-contained bash script (a Python script on Windows) that
   runs the steps in order and records its state in `<jobdir>/.qes/`:

   | File | Content |
   | --- | --- |
   | `pid` | PID of the runner |
   | `state` | `running`, `done`, `failed` or `cancelled` |
   | `step` | current step, 1-based |
   | `exit_code` | exit code of the last step |
   | `started`, `finished` | timestamps |
   | `sched_id` | batch job id (SLURM/PBS) |
   | `runner.log` | runner messages; each step writes its own `<input>.out` |

   For SLURM/PBS the same script carries `#SBATCH`/`#PBS` headers and is submitted with
   `sbatch`/`qsub`. Cancellation kills the step's process group (direct) or calls `scancel`/`qdel`.
4. `JobManager._monitor` polls active jobs: every `poll_interval_s` while someone watches the job's
   log, otherwise at least every 10 s. A poll reads the state files in one round trip
   (`read_small_files`); `pid_alive` or the scheduler's queue state distinguishes a running job from
   a vanished one (`lost`). Network errors only set `summary.poll_error`; they never fail a job.
5. When a job reaches a final state, `on_finished` downloads the useful outputs (skipping wavefunctions
   and scratch, `jobs/results.py`), runs `analysis.analyze_job`, and stores a brief summary (energy,
   gap, EOS fit, ...) for the job list.

The live log is a WebSocket (`/api/ws/jobs/{id}`) that tails the current step's output by byte
offset; `/api/ws/events` pushes job status changes so lists refresh without polling.

### Analysis

`analysis.analyze_job` dispatches on the workflow kind (`scf`/`relax`/…, `bands`, `dos`, `phonon`,
`convergence`, `eos`, `density`) and returns JSON shaped for the result components. Parsers live in
`core/parsers/` and are tested against real QE 7.6 outputs in `tests/data/`. Checks that guard
against silent errors:

- the electronic DOS integral at E_F equals the number of valence electrons (tested);
- the phonon DOS must integrate to 3·nat; otherwise a Gaussian DOS is recomputed from `matdyn.x`'s
  grid frequencies and weights and the plot says so (see `_checked_phonon_dos`);
- the cube-file charge integrates to the electron count (tested);
- units are checked against values written by `pw.x` (`test_units_match_quantum_espresso`).

### Input schema

`data/qe_schema.json` is generated from the PWgui module files that ship with QE
(`share/GUI/PWgui/modules`, which embed the official `INPUT_*.def` documentation):

```bash
python backend/tools/gen_schema.py <qe-prefix>/share/GUI/PWgui/modules backend/qestudio/data/qe_schema.json
```

Regenerate it when supporting a new QE version. q2r.x and matdyn.x have small hand-written schemas
in `core/schema.py`.

### Security model

- Single user, loopback only. The API can run arbitrary commands on every configured connection,
  so the token check is on every route, including WebSockets.
- Secrets never leave the backend: SSH passwords and key passphrases, Jupyter URLs (they embed tokens)
  and the Claude API key are stored with `secrets_store` (OS keyring, or `QES_HOME/secrets.json` with
  mode 0600) and are not included in any API response; the UI only sees `has_password: true`.
- File names from the UI are validated (`[A-Za-z0-9_.-/]`, no `..`) before they are used in paths on
  a target; shell arguments are quoted with `shlex.quote` (`executors.base.q`).
- Archives (uploaded QE binaries, SSSP tarballs) are extracted with path-traversal and link checks
  (`qe_setup._safe_extract_tar`).
- AI: requests go to the Anthropic API only on an explicit *Ask*, with the context the user sees in
  the drawer. `QES_AI_DISABLED=1` makes `ai_available()` false everywhere and the UI hides AI
  controls; the check is repeated while an answer is streaming.

## Frontend

- **Data**: TanStack Query hooks in `api/hooks.ts` wrap every endpoint; components never call
  `fetch` directly. Mutations invalidate the relevant query keys. `api/types.ts` mirrors the backend
  JSON (keep them in sync when changing a response).
- **State**: server data lives in the query cache. Cross-page working state (the structure and input
  currently being edited, the AI drawer) lives in a small zustand store (`store/app.ts`). Everything
  else is local component state.
- **Performance**: pages are lazy-loaded; Monaco (≈3 MB) and Plotly (≈1 MB, "basic" bundle: scatter,
  bar, heatmap) load only when a page needs them. The 3D viewer uses instanced meshes and canvas
  sprites for labels, so large cells stay interactive. The live SCF parser is incremental
  (`lib/liveScf.ts`) and returns the same object when nothing changed, to avoid re-renders.
- **Styling**: Mantine components and theme (`theme.ts`); light/dark/auto from Settings.

## Extending

**A new workflow.** Add a generator `wf_<kind>(scf_text, ...)` in `core/generate.py` that returns
`{"kind", "name", "steps": [step(...)], "workflow": {...}}` (the `workflow` dict is stored with the
job and passed back to the analysis); register it in `api/qe.py` (`/api/qe/workflow`); add an
`analyze_<kind>` branch in `analysis.analyze_job`; add a card to
`frontend/src/components/workflows/catalog.ts` and a result component in `pages/results/`. Add a test
in `tests/test_generate.py` and, with a real output in `tests/data/<kind>/`, a parser test.

**A new batch system.** Subclass `Scheduler` in `jobs/schedulers.py` (`submit`, `queue_state`,
`cancel`), add its header block in `jobs/runner.py`, register it in `SCHEDULERS`, and add it to the
connection form (`components/connections/constants.ts`).

**A new transport.** Implement the `Executor` interface (see the table above); return it from
`connections._make_executor` for a new connection `kind`; add the kind to `api/connections.py` and the
connection form. Make `launch_detached` truly detached and make retries safe (see the Jupyter
executor).

**A new output parser.** Add a pure function in `core/parsers/` that takes text and returns plain
JSON types (lists, not arrays; `None` for missing values), a test with a real output file, and wire
it into `analysis.py` (job results) and/or `analysis.parse_uploaded` (the *Analyze outputs* page).

**A new page.** Create `pages/<Name>.tsx`, add a lazy route in `App.tsx` and a navigation entry;
put data access in a hook in `api/hooks.ts`.
